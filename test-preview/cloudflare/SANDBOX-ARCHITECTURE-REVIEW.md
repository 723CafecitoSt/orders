## Square Sandbox preparation

`square-sandbox-plan.mjs` only builds and validates request bodies. It does not call Square, persist state or accept credentials. It builds an itemized order, rejects unsupported mixed taxable modifiers, checks the exact Square order total and location before constructing CASH payment with `autocomplete:false`, then prepares PayOrder with the approved payment ID. Completion requires validating both a completed Square order and a completed payment. Square can calculate rounding differently; any difference requires review, not a payment. Stable per-stage keys are used for requests; keys and exact immutable inputs must be durably saved before network calls, not regenerated. Network failures after a request are uncertain: retry only the identical request with the identical key and reconcile against Square before changing status or allowing a new payment. Never infer a failed charge from a timeout.

Before connecting, implement the state machine and atomic cross-device reservation, durable stage inputs and audit trail, securely bounded retries and reconciliation by identifiers, immutable server-generated snapshots, Square API credentials restricted to Sandbox and location verification, CSRF/CORS/session and rate limiting, independent security review, and actual end-to-end Sandbox tests. The previous Node prototype's CASH auto-completion flow is not established as correct for order settlement; do not deploy it. No Sandbox order or payment has been created.
