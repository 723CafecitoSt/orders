# Sandbox-only cash prototype

No production endpoints, credentials, web deployment, or real payments are enabled. Node 24+ is required for `node:sqlite`. The prototype is intentionally bound to 127.0.0.1 and is not connected to the browser application. `server.mjs` requires `SQUARE_ENVIRONMENT=sandbox`, `SQUARE_SANDBOX_ACCESS_TOKEN`, `SQUARE_SANDBOX_LOCATION_ID`, `ORDER_STATION_BACKEND_SECRET` (at least 32 bytes) and `ORDER_STATION_DB_PATH` in its runtime environment. Do not put values in files, browser code, git, logs, or chat. The local HTTP adapter is for an isolated development environment only; its shared secret and loopback binding are not production authentication, encrypted transport, authorization, or durable infrastructure. Never expose it to the internet or use real customer data. No deployment has been configured.

`POST /sandbox/cash` expects a stable `operationId` and `order.orderId` (8–64 letters, digits, underscore, hyphen), immutable order items, calculated `order.totalCents`, and `receivedCents`. Authenticate with a server-side bearer secret for the local prototype. `GET /sandbox/attempts/{operationId}` returns a sanitized status. The browser's cash button is simulation-only and does not call this service.

The service writes an operation before calling Square; creates an ad hoc order with product and modifier detail and additive per-line taxes; checks Square's returned order location, USD and total against the submitted total before creating a CASH payment; and uses separate stable Square idempotency keys for the order and payment. Underfunded cash is rejected. A pending timeout is uncertain, and retry uses the exact saved payload and keys. A changed payload or operation ID for the same order is rejected; mismatches require manual review. Confirmation requires Square's completed CASH payment with matching order, location and amount. Mixed taxable and non-taxable priced modifiers on a taxable item are rejected for review. Test Square's rounding and payment flow before connecting any frontend.

`card-verification.mjs` is a sandbox-only verification building block, not wired to a server endpoint or POS callback. Its expected amount and location must come from trusted, durable backend state created before charging. A matching Square order/payment and status is necessary but is NOT by itself sufficient to prove correlation to the requested operation: authentication, server-side operation creation, callback replay protection, immutable binding and a durable one-to-one payment claim still need implementation. Cancellation, missing transaction IDs, outages, refunds, partial payments and uncertain results must remain unresolved until securely reconciled. Do not mark paid based on a browser callback.

Remaining before a real rollout: implement strong authenticated staff identity and authorization, HTTPS, CSRF and origin controls, secure storage/rotation of a least-privilege Square token, managed durable database and backups, atomic cross-device locks shared by cash and card, immutable order and payment claim records, full reconciliation and audit trail, a reviewed way to map all modifier tax cases and refunds, an explicit production switch that stays off until authorized, and end-to-end device and backend security testing. A production access token is never supplied to the browser. A production-ready backend has not been implemented or deployed.

Run local tests without credentials or network: `node service.test.mjs` and `node card-verification.test.mjs`. They use mock Square responses. Actual Square Sandbox API behavior has not yet been tested.
