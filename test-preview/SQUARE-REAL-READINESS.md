# Square POS integration — test branch, disabled

## Status

The default button runs simulations only. `REAL_SQUARE_LAUNCH_ENABLED` and `REAL_POS_BACKEND_READY` are both false. `launchRealSquare` is intentionally not wired to a control. It cannot launch while either gate is false. No credentials or Square access tokens are stored in the browser or repository. The existing Point of Sale API application ID is public.

The prepared Android Chrome flow persists a snapshot and an operation ID before attempting an Android Intent, requires online status and the independent test origin, sends a final USD amount and the order note, and records a callback response without treating it as verified. Unmatched, incomplete, repeated or tampered callback responses do not prove a payment. Returned IDs and cancellation/error reports remain unverified and unresolved; the app blocks another attempt until reconciliation. Restoring an operation restores its order. Actual backend reconciliation and an operator recovery path are not implemented, and the client-only lock is not sufficient across devices or browser profiles.

The test origin holds its own browser data. Simulated attempts and any future real-test attempts use different local storage keys. This does not synchronize with or migrate production data. Do not use real customer data in testing.

## Backend contract to implement before enabling

1. Use an authenticated seller-only HTTPS service with a durable database and atomic per-order/payment locks, unique operation IDs, and idempotent transitions. The server—not the browser—must own the expected amount, currency, seller/location, order identity and current state. It must create a pending attempt before launch. Only one unresolved attempt may exist for a given order across all devices. Backend unavailability must prevent a real launch; a timeout is not evidence that no payment occurred.
2. Receive the browser's return as an untrusted report, correlate operation metadata with the server-created pending attempt, and retain callback IDs without accepting a client-supplied amount or status as authoritative. Do not put Square tokens, authentication secrets, or private transaction records in URLs, browser code, or GitHub.
3. Using a least-privilege Square production token kept in the server's secret store, use the Square server transaction ID to retrieve the corresponding Order, follow its tender payment IDs and retrieve the Payments. Verify seller and location, `COMPLETED` status, USD, charged amount (including separately handled tips/refunds), order-to-payment linkage, and a one-to-one association to the pending operation; record exact provider IDs and the verified evidence. A note alone is not a unique or authenticated proof. Handle partial payments, retries, disputes, refunds and mismatch as reconciliation-required. Never mark paid on callback alone.
4. The documented order/payment retrieval method does not work for cash POS payments, and the server ID can be absent for offline transactions. Keep these unresolved and provide a secure operator reconciliation process rather than automatically declaring paid or retrying. The test's planned real flow must require connectivity and card tender; POS behavior still requires validation on device.
5. Provide an authenticated, auditable recovery flow that checks Square before releasing any pending or uncertain attempt; do not unlock solely on a browser error, lost callback, elapsed timeout, or a cancellation report. Cross-device locks must survive reloads, reinstallations, concurrency, and lost browser storage. Use replay-safe callback processing and avoid clearing the original order until the backend confirms outcome.
6. Verify that Square does not add taxes or fees again, and that the amount actually shown before charging equals the already tax-inclusive 723 amount. Point of Sale API availability of a switch for automatic fees must be confirmed for Android. Do not assume that sending a total prevents fees or taxes. Explicitly decide how Square tips and its sales/tax reporting are handled before a live test.

References: https://developer.squareup.com/docs/pos-api/web-technical-reference and https://developer.squareup.com/docs/pos-api/payments-integration.
